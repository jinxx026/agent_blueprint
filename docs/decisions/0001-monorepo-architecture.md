# ADR-0001：采用模块化单仓库架构

状态：Accepted  
日期：2026-08-30

## 背景

AgentBlueprint 同时包含后端运行时、前端配置界面、规范文档、示例模板和部署配置。项目早期需要频繁修改跨模块契约，例如 Blueprint Schema、API 类型和评测格式。

## 决策

采用单 Git 仓库，并在仓库内部保持清晰模块边界：

```text
backend/   frontend/   docs/   examples/   deploy/
```

后端初期采用模块化单体，而不是拆分微服务。Compiler、Runtime、Knowledge、Tools、Governance 和 Evaluation 保持独立 Python 包边界，通过明确接口交互。

## 原因

1. Blueprint 和 API 契约变更可以在一个提交中同步修改实现、测试和文档。
2. 本地开发和私有部署更简单，适合第一批小型企业试用。
3. 模块化边界仍允许未来把高负载 Runtime 或 Knowledge 摄取拆为独立服务。
4. 单仓库便于运行端到端测试和生成统一版本。

## 后果

正面影响：

- 开发、调试和部署成本较低。
- 示例和规范与代码版本保持一致。
- 初期无需维护分布式事务和服务发现。

需要承担：

- 必须通过代码结构和依赖规则防止模块互相随意引用。
- 数据量和团队规模增加后，部分模块可能需要拆分。
- 持续集成需要根据目录变化选择性运行任务，避免构建时间不断增长。

## 未来拆分条件

满足以下任一条件时重新评估：

- Runtime 与管理 API 需要明显不同的扩缩容策略。
- 文档摄取任务影响在线请求稳定性。
- 单次部署无法满足企业网络隔离要求。
- 独立团队需要对某模块建立单独发布节奏。

在这些条件出现前，不提前引入微服务复杂度。
